# RAG 실험 계획

> 과제 제출물 "RAG 실험 계획"이에요. 무엇을 왜 비교했고, 무엇을 고정했고, 어떻게 재고 기록했는지를 한곳에 모았어요.
> 실험별 전체 수치는 [실험기록.md](실험기록.md), 진행 중 만난 문제는 [회고.md](../회고.md)에 있어요.

<br>

## 1. 목적

금융 문서 23개를 검색해 **근거(파일명·쪽)와 함께 정확히 답하는 RAG Agent**를 만들고, 각 설계 선택이 품질·비용에 주는 영향을 숫자로 확인해요.

| 질문 | 확인하는 실험 |
|:---|:---|
| 어떤 청킹·검색이 정답 근거를 가장 잘 찾나? | E1 ~ E4 |
| 근거를 찾은 뒤 답변을 더 정확하게 만드는 방법은? | E5 ~ E7 |
| Agent 구조가 기본 RAG보다 나은가? 추가 비용만큼 가치가 있나? | E8 |
| 더 가벼운 모델로 품질을 유지하면서 비용을 줄일 수 있나? | E9 |

<br>

## 2. 데이터

### 검색 대상 PDF (`01_data/`, 23개)

| 문서 | 개수 | 특징 |
|:---|:---:|:---|
| 금융용어집 | 1 | 용어 · 정의 |
| 증권 표준약관 | 15 | 조항 단위, 별첨 참조 |
| 금융생활 가이드북 | 1 | 표 · 그래프 · 예시 많음 |
| 추가 보고서 (주택연금, 퇴직연금, 정책금융, 자영업자 부채, 보험약관, 채무조정) | 6 | 통계표 · 그래프 · 수식 |

**검색 범위 조건 (과제 규칙):** 기본 positive(POS001~060)·negative(NEG) 문항은 **용어집 + 표준약관만** 검색해요. 나머지 문항은 23개 전체를 검색해요. 이건 실험 조건이라 기본 RAG와 Agent 모두 밖에서 똑같이 정해 줘요.

### 질문 세트 (`05_golden_set/`)

| 세트 | 문항 (평가) | 출처 | 용도 |
|:---|---:|:---|:---|
| `golden_set_table_image` | 189 | **직접 작성** (표·그림·수식) | 검색 평가 |
| `golden_set_paragraph` | 100 | **직접 작성** (본문 문단) | 검색 평가 |
| `golden_set_provided` | 180 (148) | 강의 제공 질문·답안 변환 | 검색 평가, 답변 평가 표본 추출 |
| `golden_set` | 20 | `provided`에서 뽑은 표본 | **튜닝셋**: 답변·프롬프트를 고칠 때 봄 |
| `provided --sample=30` (seed 0) | 30 | 튜닝셋 제외 무작위 | 처음 보는 문항 확인 1 |
| `provided --sample=30 --seed=1` | 30 | 튜닝셋·seed 0과 **겹치지 않게** | 처음 보는 문항 확인 2 (seed 0을 보고 고친 뒤) |
| `provided --sample=30 --seed=2` | 30 | 튜닝셋·seed 0·1과 겹치지 않게 | 최종 비교(E10-b) |
| `paragraph`·`table_image --sample=30` | 30 + 30 | **직접 만든** 골든셋에서 무작위 | 최종 비교(E10-b), 직접 만든 셋을 제공 세트와 따로 평가 |

- 직접 만든 골든셋(289문항)과 제공 세트는 **따로** 평가해요.
- 기준 답안이 문서에 없는 상식·계산을 필수로 요구하는 2문항(ADD-SE06, ADD-PF08)은 답변 평가에서 빼요 (`05_golden_set/excluded_cases.json`에 이유 기록). 질문·기준 답안은 검색 DB에 넣지 않아요.
- 직접 만든 문항은 질문, 기준 답변, 근거 파일·쪽, 근거 유형(paragraph / table / image / formula / none)을 적고 PDF 원문과 대조해서 검수했어요.
- 문서로 답할 수 없는 문항(none)에는 기대 대응(`expected_behavior`: 거절, 되묻기, 최신 자료 안내 등)을 기록했어요.

## 3. 기준 설정

모든 비교는 아래 기준에서 **한 가지만 바꿔서** 해요.

| 항목 | 기준 값 |
|:---|:---|
| 추출 | pdfplumber + 깨진 표·그림만 Gemini (숫자 검증) → `04_extracted/pages.jsonl` |
| 청킹 | 구조 반영 분할 (표·그림 따로, 본문은 쪽 단위 `RecursiveCharacterTextSplitter`) |
| 임베딩 · DB | `gemini-embedding-2` · Chroma |
| 검색 | k=5, fetch_k=20, MMR λ=0.5, Hybrid 벡터:BM25 = 0.5:0.5, BM25는 Kiwi 토큰화 (강의 스크립트와 같음) |
| 답변 · 채점 LLM | `gemini-3.6-flash` |
| 답변 프롬프트 | 근거만 사용, 문장마다 `[파일명 p쪽]`, 근거가 없으면 "찾을 수 없다" (`--prompt=base`) |

실험을 진행하면서 좋은 결과가 확정되면 기준을 갱신했어요 (예: E1·E2 뒤로 300/50 + Hybrid, E6 뒤로 이웃 청크 ±1).

## 5. 평가 지표

### 검색 (`evaluation/retrieval_eval.py`, LLM 없음)

| 지표 | 측정 방법 |
|:---|:---|
| hit@1 / hit@3 / hit@5 | 상위 k개 안에 정답 청크가 하나라도 있으면 1 |
| precision@5 | 상위 5개 중 정답 청크 비율 |
| recall@3 / recall@5 | 정답 쪽들 중 상위 k개가 덮은 비율 |
| MRR | 첫 정답 청크 순위의 역수 |
| latency | 질문 임베딩을 뺀 순수 검색 시간 |

**정답 청크:** 정답 파일의 정답 쪽에 있는 청크. 약관은 조항 ID → 약관 파일·조항 시작 쪽, 용어집은 파일 단위. 질문마다 계산해서 평균, 난이도별·근거 유형별로도 나눠 봐요.

### 답변 (`evaluation/answer_eval.py`, 채점 LLM 1회)

| 지표 | 측정 방법 |
|:---|:---|
| correctness | 기준 답안과 비교, LLM 채점 1 / 0.5 / 0 |
| faithfulness | 답을 주장으로 쪼개서 검색 근거로 뒷받침되는 비율 (RAGAS Faithfulness와 같은 방식) |
| must_include | 꼭 들어가야 할 내용을 충족한 비율 |
| must_not | 피해야 할 오류를 하나라도 했으면 1 |
| behavior_ok | 기대 행동(근거 인용, 거절, 되묻기, 최신 자료 안내 등)을 지켰나 |
| citation_ok | 답에 적은 `[파일 p쪽]` 중 정답 쪽이 있나 (규칙으로 계산) |
| **outcome** | 성공 / **검색 실패** / **답변 실패**. 실패면 LLM에 넘긴 근거에 정답 쪽이 있었는지로 나눠서, 근거를 놓친 경우와 근거를 찾고도 잘못 쓴 경우를 구분 |

RAGAS 대신 채점 LLM 1회를 쓴 이유: 골든셋에 기준 답안·필수 내용·피할 오류·기대 행동이 이미 있고, 지표마다 LLM을 여러 번 부르는 RAGAS보다 호출이 적고 토큰을 정확히 기록할 수 있어서예요.

### 자원 (기본 RAG vs Agent)

문항마다 **LLM 호출 수, 검색 횟수, 입력·출력 토큰(생각 토큰 포함), 전체 시간**을 더해서, "추가 자원 대비 품질이 얼마나 올랐나"를 봐요. 금액은 [비용기록.md](비용기록.md)에 실행마다 자동으로 남아요.

## 6. 결과 기록

| 파일 | 내용 | 저장 방식 |
|:---|:---|:---|
| `07_eval/runs.jsonl` | **실행 한 번 = 한 줄**: `run_id`, 실행 시각, 질문 세트, 문항 수, 설정, 요약 결과, 토큰, 비용 | 이어 붙임 (지워지지 않음) |
| `07_eval/{세트}/retrieval_rows.jsonl` | 질문 × 청킹 × 검색마다 점수와 가져온 청크 | 덮어씀 |
| `07_eval/{세트}/answer_rows.jsonl`, `agent_rows.jsonl` | 문항마다 질문, 답변, 넘긴 청크 ID, 점수, 채점 이유, 시간, 사용량 (Agent는 분류·경로·검색어도) | 덮어씀 |
| `07_eval/{세트}/*_summary.txt` | 사람이 읽는 요약 표 | 덮어씀 |
| `docs/비용기록.md` | 유료 호출마다 토큰·비용 한 줄 | 이어 붙임 |

**설정 기록 (`runs.jsonl`의 `params`):** 모델명(답변·채점·임베딩), 프롬프트 규칙 묶음, 청킹 설정과 **청크 파일 지문(`chunks_md5`)**, 검색 방식·k·fetch_k·가중치, 이웃 청크 수, 모드(rag / agent), Agent 설정(재검색 상한, 생각 수준)

**연결:** 같은 `run_id`가 `runs.jsonl`(설정 + 요약)과 `*_rows.jsonl`(문항별 결과)에 들어가서, 실험 ID 하나로 설정 → 문항별 결과 → 요약을 따라갈 수 있어요.

저장 형식은 JSONL이에요. 줄마다 JSON 하나라서 git diff로 바뀐 점이 보이고, `pd.read_json(..., lines=True)`로 바로 비교할 수 있어요.

## 7. 비교 원칙

1. **한 번에 하나만 바꾸기.** 질문 세트, 검색 대상 PDF, 채점 방법은 그대로 두고 기준 대비 한 요소만 바꿔요. 여러 요소가 바뀌는 E8은 전체 구성의 효과로 해석해요.
2. **고친 셋과 확인하는 셋 나누기.** 튜닝셋(`golden_set` 20)을 보고 고쳤으면, 처음 보는 30문항으로 다시 재요. 그 30문항을 보고 또 고쳤으면, **겹치지 않는** 새 30문항(seed 1)으로 재요.
3. **잡음 기준.** 같은 설정을 다시 돌려도 1~2문항은 0.5 ↔ 1.0으로 흔들려요(실측). 그래서 20~30문항에서 1~2문항 차이로는 우열을 정하지 않고, **원인을 설명할 수 있는 변화**나 **여러 번 돌려도 재현되는 차이**만 근거로 삼아요 (예: POS080 이웃 청크, NEG010 되묻기).
4. **실패 문항은 직접 열어 보기.** 자동 분류(검색 실패 / 답변 실패)를 확인하고, 실제 원인을 실험기록에 적어요.
5. **측정이 맞는지도 확인.** 검색 없이 답한 경우는 faithfulness 계산에서 빼는 것처럼, 지표가 상황에 맞지 않으면 고치고 그 사실을 적어요.
